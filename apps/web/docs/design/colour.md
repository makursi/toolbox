# 色彩 token 与明暗配色

> **管什么**：颜色的值（token）与模式（浅色 / 深色）怎么选、怎么存。**和它一起读**：`apps/web/docs/design/components.md`（配色开关与触控目标）、`apps/web/docs/design/assets.md`（唯一允许保留自己颜色的东西）。

## 值（token）

暖色单色（warm monochrome）。**值定义在 `apps/web/src/lib/tokens.ts`**——一个与组件引擎无关的纯模块，加一个对比度纯函数。**两个组件层都读它，它也是唯一声明值的地方**（#126）：旧层在 TypeScript 侧读（`apps/web/src/app/theme.ts` 的 `createTheme` 与 `cssVariablesResolver`），新层读同一批值——根布局把模块发成文档里的自定义属性，`apps/web/src/app/globals.css` 再用一个 `@theme inline` 块把新层的工具类名映射上去。**样式表里再写一个十六进制值就是第二个主人**；`tokens.test.ts` 盯的就是这件事（#127）。只有新层在用的圆角与字阶还留在 Tailwind 的默认值上，#116 显式重定。

**没有强调色（accent color）**：界面上唯一的颜色只用来表达语义，也就是错误。

**一个例外，而且是明知的选择**：工具封面与**站点标记**都是外部素材（见 `apps/web/docs/design/assets.md`），保留它们自己的颜色，不进这套调色板、也不受"无强调色"约束；工具自己渲染的资源预览同理（先例：image-converter 文件行里的 40×40 缩略图，见它的 `rules.md`），那些就是访客自己的图片像素。换句话说，界面本身仍然只有一个颜色在说话；封面、标记与缩略图是页面上的一幅图，不是界面的一部分。（标记把这条例外从"卡片里的配图"扩到了页头与浏览器标签，那是 2026-09-18 有意的扩大，理由见 `docs/adr/0011-the-mark-is-a-supplied-illustration.md`。）

对比度是**算出来的，不是看出来的**：正文 17.47:1（浅）/ 15.20:1（深）；次要文字 5.14:1 / 6.48:1；占位符 4.61:1 / 5.65:1；主按钮实心填充两个模式都是 17.33:1。AA 对正文的要求是 4.5:1。

有**两次测量直接改变了设计**，而不是被记录成"已知问题"绕过去：参考方案建议的次要色 `#787774` 只有 4.14:1，被换掉了；第一版占位符颜色 `#8a877f` 只有 3.44:1，也被换掉了。**以后新增任何颜色，都要用同样的方式先测量**（见 `apps/web/docs/design/checklist.md`）。

**错误色是量出来的，而且是两个值。** 界面唯一的颜色就是错误，而它此前一直是**借 Mantine 的**（两处 `Alert color="red"`）——本仓从来没有一个自己量过的错误色可以搬，所以 #126 把它记成一个缺口、没有编一个值，#116 给它命名并测量：**`#c92a2a`（浅）/ `#ff8787`（深）**。为什么是两个值，是算出来的而不是挑出来的：**没有任何一个红能在两套配色里同时作为实心控件的底色过 AA**（实测：`#c92a2a` 对浅色纸 5.05:1，但对深色墨只有 3.31:1；`#ff8787` 对深色墨 7.81:1，但对浅色纸只有 2.14:1）。所以浅色那套用一个深红、深色那套用一个亮红，各对着自己那套的纸/墨算。两个值**同时**也满足"错误当文字用"：`#c92a2a` 在浅色画布上 5.05:1，`#ff8787` 在深色画布上 7.81:1。

**一条量出来的缺陷，因此新层的实心错误变体不画**：注册表那个 `destructive` 变体在深色下要的是 `bg-destructive/60`——六成不透明的红压在近黑的画布上。实测合成出来是 `oklab(0.756287 0.136238 0.0525888 / 0.6)`，对着本站深色那套的纸（近黑）只有 **3.60:1**，**过不了 AA**。这不是选错了红：六成不透明的**任何**红压在近黑画布上，合成色都会往画布靠，而它的标签正好也是那个近黑的纸——换亮红、换深红都到不了 4.5:1。注册表自己的默认值也一样：它深色的 `destructive` 是 `oklch(0.704 0.191 22.216)`，纯白压在上面只有约 2.9:1，也就是**这个变体的深色形态在它自己的默认值上就不过 AA**。所以结论是：本站的错误面（今天两处 `Alert`）是**画布上的文字**，7.81:1 达标；实心的 `destructive` 按钮要进界面，就得有本仓自己的组件，而不是注册表那个默认变体——这一条是决定，不是待办。

**每一个值都要说清它对着哪个表面算的**，因为同一个次要色在两块表面上不是一个数：#116 起把配对写全（下表），不再写一个孤立的比例。AA 对文字要 4.5:1。

**这张表里的数字不再靠人守**（#127）：`apps/web/src/lib/__tests__/tokens.test.ts` 把界面上实际用到的每一对都列了出来，对着 `src/lib/tokens.ts` 算一遍，两套配色都要过 AA；表里那个被豁免的发丝线在测试里是**显式豁免**，并且测试会要求豁免的那一对确实低到 3 以下（差一点就该修，不是该豁免），同时要求每个 token 至少出现在一对里——所以「界面上加了一对、测试里忘了加」会红，而不是悄悄漏过。上面那个不画的实心错误配对也写在注释里，说明它为什么不在表内。下表是 #116 那一次的读数；真正的守卫是那条测试。

**发丝线那条低是有意的，也是写明的**：它只做装饰（卡片的边、分隔线），不承担"这是控件边界"的语义，所以 WCAG 1.4.11 的 3:1 对它不适用。**但输入框的边框是它的边界**，而新层里 `--color-input` 现在也是发丝线（1.11:1）——这是**记下来的未决项**，不是遗漏：#116 保留了它，因为旧层的输入框今天就是这个值，试点期让两层长得不一样比留一个已知项更糟；层换完之后要么给它一个过 3:1 的值，要么让输入框的填充承担边界（今天填充与画布的差也只有 1.1 左右）。聚焦环取正文色（17.47:1），它承担的那条是有余量的。

**纯黑与纯白在新层里被挡住，而不是靠自觉。** 禁纯 `#000000` / `#ffffff` 是强制项，换组件层不是重开它的理由（`apps/web/docs/design.md`），而注册表发来的组件不是我们手改的东西——它自己的变体里就写着 `text-white`。所以这条禁令落在值这一层：`globals.css` 里 `[data-layer="primitive"]` 把 Tailwind 的 `white` / `black` 重指到本站的纸与墨。**它是有作用域的，故意的**：封面生成器预览框上的 `bg-white` 画的是**导出产物的底色**，而"导出的图片像素不算"正是同一条规则早已写下的例外——全局重指会让访客下载到的文件悄悄变一个颜色。

**为什么旧层这一端仍是 TypeScript**：Mantine 的变量由 `createTheme` 加一个 `cssVariablesResolver` 在**运行时**写到文档里，位置在我们的样式表之后——所以在 CSS 里直接覆盖 `--mantine-color-body` 会输掉层叠，resolver 是官方支持的路径，也是唯一稳赢的路径。这个理由只解释**旧层这一端为什么不能用样式表**，不再解释值住在哪里：值住在模块里（#111 否掉的是"两个颜色主人"，不是"样式表"本身）。新层那一端没有这个限制，它的名字映射是静态的，值来自根布局发出的同一份模块。

## 模式（明暗配色）

**配色只有唯一一个主人：Mantine 的配色管理器加它写在 `<html>` 上的 `data-mantine-color-scheme` 属性**（#126）。`ColorSchemeScript` 在首屏前读持久化的选择（没有选择时读操作系统，那是只有它能读的东西）并写下这个属性。**新层不另立机制**：`globals.css` 用一条 `@custom-variant dark` 把 Tailwind 的 `dark:` 变体定义在**同一个属性**上，而不是默认的 `prefers-color-scheme`，也没有 `.dark` 类、没有第二套主题库。留两套的代价不是风格问题：访客一旦手动选了与系统相反的配色，两个定义就会当场互相矛盾。

`ColorSchemeScript` 与 provider 都设为 `auto`：**默认跟随操作系统**。页头右侧有一个两态开关（`ThemeToggle`，带 `.touch-target`；**按钮自 #163 起是新层的 Primitive**，框是量出来的 32×26、1px 发丝边框、表面色填充、4px 圆角、14px 字——为什么不是从注册表的档位里挑的，见 `apps/web/docs/design/components.md`），**只有图标**（浅色下是月亮、深色下是太阳），图标写的是**它将要切到的模式**。**一旦点过，就不再跟随系统**，直到清除站点数据——这是知情的取舍，见 `docs/adr/0008-manual-colour-scheme-switch.md`。

持久化由 Mantine 自带的 `localStorageColorSchemeManager` 完成（就是 provider 的默认值，没改一行配置），`ColorSchemeScript` 在首屏前读取它，所以没有闪白也没有 hydration 不匹配。

**名字由样式表切，不由 JS 状态切**：图标与 `sr-only` 的名字都按模式各备一份、都在 DOM 里，`[data-mantine-color-scheme]` 决定哪一份活着。服务端不可能知道系统配色，所以任何在渲染期读 scheme 的做法，要么 hydration 不匹配、要么先撒一句谎再自我纠正。也因此**它没有 `aria-label`**：写在组件里的 `aria-label` 是一个固定字符串，总有一种配色下会与实际显示的模式不符；而两份 `sr-only` 文字正好可以写成完整的句子（「切换到深色」），这是以前那个可见的词负担不起的。**这条理由与哪个库渲染这个控件无关，所以它不随组件层走**（#126）。

任何 token 都必须**先补齐两个模式**才能上线。禁止纯 `#000000` 与纯 `#ffffff`（见上：新层里由作用域挡住）：两者都撑不起层次；浅色画布之所以是暖白（bone），正是为了让白卡片能落在它上面。任何一"节"都不允许在页面中途翻转成反色主题。

## 圆角与阴影（#116 的显式决定）

**圆角是两个值，名字落在注册表组件真正会用的那两个上**：`--radius-md: 4px`（控件）、`--radius-lg: 8px`（容器），另有 `--radius-sm: 4px` 与 `--radius-xl: 8px` 跟上。注册表自己的默认是**一个**值（`--radius: 0.625rem`）再由它算出其余，落到控件上是 8px、容器上是 10px；这条被换掉，因为本仓的规则是"容器一个圆角、控件一个更小的圆角"，理由（药丸形控件放在方正卡片里读起来像装饰）没有随组件层改变。`rounded-md` 是注册表组装控件时用的名字，`rounded-lg` / `rounded-xl` 是它组装容器时用的名字，所以两个值就写在这两个名字上。

**阴影是一个位置，不是缺席**：站点只有一处阴影，就是卡片 hover 时那一道 4% 的 `lift`，静止时什么都不投影。注册表最小的两档（`--shadow-2xs` / `--shadow-xs`）被重指成不可见的阴影，这样生成来的组件不会靠"要它自己的默认值"把阴影带回来；更大的阴影仍然要一次显式决定——那正是这条位置存在的意思。

## 从注册表读到的默认值（#116 的第一步）

取值之前**先把对方的默认值读了一遍并留档**，这样"我们以默认值为起点"是一句有出处的话，而不是一句自述。

- **出处**：`components.json` 的 `style` 是 `new-york-v4`（base `radix`、`baseColor` `neutral`）。它的风格条目 `https://ui.shadcn.com/r/styles/new-york-v4/index.json` 里 `cssVars` **是空的**——颜色值不在风格条目里，而在基础色条目 `https://ui.shadcn.com/r/colors/neutral.json` 的 `cssVars.light` / `.dark`（同一份 JSON 里还有 `inlineColors`，两者一致）。2026-10-05 经本机 launcher 取到。
- **读到的东西里，有一条直接替我们做了决定**：浅色 `background` 是 `oklch(1 0 0)`，就是**纯白**。ADR-0007 记的"上一次尝试留下一个纯白画布"当年量的是另一个风格（`radix-nova`），而现行风格**依然是纯白画布**——所以"禁纯白"这条强制项不是历史包袱，它今天仍然在挡同一个默认值。
- **整份默认色是消色的**（chroma 全为 0）：`foreground oklch(0.145 0 0)`、`border oklch(0.922 0 0)`、`radius 0.625rem`；深色 `background oklch(0.145 0 0)`、`border oklch(1 0 0 / 10%)`、`input oklch(1 0 0 / 15%)`、`destructive oklch(0.704 0.191 22.216)`。
- **被换掉的两条硬理由**：深色的 `border` / `input` 是**纯白加透明度**（`oklch(1 0 0 / 10%)`），撞禁纯白；浅色画布是纯白，撞同一条。其余（消色而非暖色、10px 圆角、`destructive` 的值）是**取舍**，按上面两张表和本节逐条替换。
- **因此没有一条默认值留在本站的调色板里**，包括 `destructive`：本仓的错误色是两个按各自配色量出来的值。留下的只有名字——`background` / `foreground` / `primary` / … 由 `globals.css` 的一个 `@theme inline` 块映射到本站的属性上。
